## 定位与修复

同一身份地址的本机对照：默认 Node fetch 约 10.5 秒报 `UND_ERR_CONNECT_TIMEOUT`；系统 curl 返回 200，约 3.94 秒；curl IPv4 约 2.42 秒，Node HTTPS 指定 IPv4 约 2.91 秒。DNS 同时返回 IPv6 与 IPv4。仅将地址族尝试窗口从 250 ms 增至 2000 ms 仍超时；采用 IPv4 优先并保留地址族自动选择后，Node 对身份、直接母公司、最终母公司接口分别约 2.20、1.71、1.55 秒返回 200。

观测将问题定位到本机 Node 与该双栈端点的连接路径，不代表所有网络的 IPv6 均不可用。仅 GLEIF 独立 MCP 子进程增加：

```text
--dns-result-order=ipv4first
--network-family-autoselection-attempt-timeout=2000
```

保留 IPv6 回退与 TLS 校验，不硬编码 IP、不改系统网络，不影响模型与台账进程。依据 [Node DNS 文档](https://github.com/nodejs/node/blob/main/doc/api/dns.md)及 [Node 网络文档](https://nodejs.org/download/release/v24.1.0/docs/api/net.html)，未新增依赖。

增加最多两次尝试：默认单次 20 秒，总预算 41 秒；配置上调时总预算最多 60 秒，低于宿主 MCP 的 65 秒期限。仅重试暂时性网络/响应体中断和 HTTP 408、429、500、502、503、504；遵守短 Retry-After，超过 5 秒的服务限流等待直接报告失败，不提前重试。404、证书错误、JSON 格式错误不重试。没有静态或缓存结果冒充成功。

返回的 `network` 回执包含 URL、实际次数、每次耗时、HTTP 状态或错误码。HTTP 200 响应头不等于完整成功，响应体中断仍记录错误。UI 原始凭证及报告保留这些字段。
